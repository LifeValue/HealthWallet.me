## Notes per question

**Q1. llama.cpp LoRA**
- The server side is mature: multi-adapter loading, scaling, global and per-request hot-swap (#1–3). Per-request swaps prevent batching, which barely matters for a single-user on-device app.
- aLoRA: a PR (#15327) appears merged, limited to one aLoRA per slot (#5). This was not confirmed in ggml-org.
- Multimodal plus LoRA: no primary source this run confirms or denies that a text-side GGUF LoRA works alongside an mmproj in libmtmd. The server README is silent (#4).
- Working hypothesis, not verified: a language-model-only LoRA should work, because the mmproj is a separate file and the LoRA attaches to LM tensors.
- No evidence found that LoRA can be applied to the vision tower or projector at runtime. Vision-side changes look like they need merge-then-reconvert (#6–7).
- Quantised base + F16 adapter quality: not evidenced this run. The only guidance is llamadart's advice to validate on the deployed quant (#15).
- `llama_adapter_lora_init` C-API details: not fetched.

**Q2. Merge-then-quantise**
- The documented path is: merge the LoRA into the HF weights, run `convert_hf_to_gguf.py` for the text model, run it again with `--mmproj` for the projector, then quantise the text GGUF to Q4_K_M and keep the mmproj at F16/BF16 (#7, #9, #10).
- There is one unresolved 2025 failure report on Qwen2.5-VL (garbage "@" output) (#8). Treat it as a risk to test against, not as a current bug.
- Unsloth supports Qwen3-VL fine-tuning, and Qwen3-VL GGUF has worked in llama.cpp since 2025-10-30 (#10). The exact `save_pretrained_gguf` behaviour for VL (whether it emits the mmproj) was not verified, because the doc fetch redirected and the budget ran out.
- Size trade-off: Apple quotes about 160 MB per adapter; a LiteRT example sidecar was 24.8 MB at rank 16 (#18, #21). A full re-quantised 2B–4B model is GBs (training knowledge, not evidenced this run). Merging means users re-download the whole model for every update.
- No quantitative quality-loss figures for quantising fine-tuned models were found.

**Q3. llamadart**
- Yes: 0.15.6 (around 2026-10-21) has a full LoRA API on the llama.cpp backend, covering load-time and runtime use, stacking, scaling, and URL or `hf://` sources with cached download (#11–14).
- The LiteRT-LM backend is limited to one load-time text LoRA (#14).
- aLoRA is unsupported (#14).
- How LoRA interacts with mmproj is undocumented (#15). Test it.
- Other Flutter bindings: not searched (budget).

**Q4. Other runtimes**
- **Apple Foundation Models**
  - The biggest change since May 2026: toolkit 26.0.0 is labelled the last release and does not work with OS 27+ (#17).
  - Combined with the "one adapter per system-model version" rule (#18), a custom adapter is a dead end for OS 27 unless Apple publishes a successor. None was found.
  - The adapter also needs an entitlement (#18) and is text-only per the docs (#19).
  - OS 27 adds image prompts to the base model (#20).
- **LiteRT-LM**
  - LoRA is architecturally supported, per Session.
  - Current reports show silent no-op LoRA on Gemma 4 E2B GPU bundles (open, 2026-08) (#21) and a reported 6 MB adapter cap (#22).
  - Low readiness for production VLM fine-tunes.
- **ONNX Runtime GenAI:** multi-LoRA via `SetActiveAdapters`, with Olive conversion (#23). Mobile and VLM coverage unverified.
- **ExecuTorch:** 1.0 has shared-weight LoRA `.pte` export (#24). Older evidence.
- **Not covered:** MLX-Swift, MediaPipe LLM Inference, Cactus, Nexa (budget).

**Q5. Licences**
- **MedGemma (HAI-DEF Terms):** a fine-tuned adapter or merged model is a Model Derivative, and shipping it is Distribution.
- Distribution carries pass-through restrictions, an Agreement copy, notices, possible Health Regulatory Authorization, a ban on uses that make Google a device "manufacturer", remote restriction rights, and deletion on termination (#25–28).
- Not fetched this run: the Gemma Terms of Use themselves, and Qwen3-VL's Apache-2.0 licence on its model card. Both remain unverified beliefs.
