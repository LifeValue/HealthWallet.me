## Notes per question

**Q1. llama.cpp state.** The native GBNF converter is still a subset implementation that fails silently (rows 1-3), and the current README still lists the same structural gaps: nested $ref, anyOf mixed with properties, number bounds, prefixItems. enum and minItems/maxItems are not listed as limitations, and the docs examples use minItems/maxItems as repetition bounds. Recent 2026 issues (rows 9-13) show two silent-failure modes that bear directly on hardening JSON output: a large $ref/$defs schema can make the server drop the constraint entirely (#21228), and the grammar is not applied when thinking is on (#20345). There are also crash/OOM bugs on deep nesting and large repetition bounds (#29690, CVE-2026-52130; #29462). I did not verify open/closed status or fix commits, so the next round should check each issue before treating it as current. llguidance is the more complete engine: it errors on unsupported keywords instead of dropping them, has a Lark CFG, and is fast (rows 6-8). It needs a Rust toolchain at build time and has different defaults (additionalProperties true, property order kept). Lazy grammars and grammar triggers exist: llamadart exposes `grammarLazy`/`grammarTriggers` (row 29). The README does not document them, and I did not retrieve a primary llama.cpp doc on them. Performance: old 2025 data shows native llama.cpp grammar roughly doubling per-token time on an 8B model (row 15). llguidance mask cost is around 50 us per token (row 7). I found no current benchmark on mtmd/multimodal plus grammar, and no evidence either way of grammar interacting badly with image prefill.

**Q2. Accuracy.** Recent evidence (2025-2026) mostly says constrained decoding helps or is neutral at 0.6-8B when the schema and prompt are reasonable (rows 16, 18). It fixes form but not semantics (row 19). One 2026 paper reports accuracy loss and large latency at 7-9B (row 22, snippet only), and a cited "constraint tax" paper (arXiv 2605.26128, secondhand, not read) claims losses below 3B. The best-evidenced mitigation is two-step draft-then-constrain (row 21). Reasoning-field-first and field-ordering patterns came up in no source I retrieved, so they remain unverified beliefs. Note that llguidance keeps schema property order (row 8) while the native converter reorders required fields first, which matters if a "reasoning before answer" field order is used. I did not retrieve the original "Let Me Speak Freely?" paper; the search failed.

**Q3. FHIR schema design.** There is direct prior art. A MIE 2026 paper does CFG-guided FHIR generation (row 23), but its results were unread because the fetch failed. Infherno deliberately avoided a full FHIR grammar as too costly and used library-backed generation (row 24). That supports the current team approach of a simplified intermediate schema plus deterministic mapping, though only indirectly. I retrieved nothing on validators (HAPI, fhir.resources, Dart FHIR packages) or on terminology enums against post-hoc lookup; budget ran out.

**Q4. Other runtimes.** Apple Foundation Models (2026 docs) adds on-device image understanding, @Generable guided generation and a custom-model provider via Core AI (row 25). This is a significant 2026 change, but it applies to Apple's model or Core AI-exported models, not to llama.cpp GGUF. LiteRT-LM has llguidance-based JSON Schema/Lark/regex, with live bugs (rows 27-28). The app's current Dart binding (llamadart) cannot use LiteRT-LM constraints yet (row 30). ONNX Runtime GenAI uses llguidance (row 31, low confidence). MLX goes through Outlines (row 32). ExecuTorch and MLC LLM/XGrammar on mobile: no evidence retrieved.
