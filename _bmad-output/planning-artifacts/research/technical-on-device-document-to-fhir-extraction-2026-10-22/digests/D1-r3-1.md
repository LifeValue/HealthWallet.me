## Notes per question

**Q1, NuExtract.**
- **Sizes and licences.** NuExtract 2.0 has three sizes (finding 1):
  - 2B, on Qwen2-VL-2B, MIT, commercial use allowed
  - 4B, on Qwen2.5-VL-3B, Qwen Research License, **not commercial**
  - 8B, MIT
- **NuExtract3 has replaced it.** It is a single Qwen3.5-4B fine-tune under Apache-2.0 (finding 3). It is a document VLM covering extraction and OCR-to-Markdown. NuMind's own numbers put it well above Qwen3.5-4B and Gemma-4-E4B on structured extraction, with far fewer failed outputs: 27 against 229 for Qwen3.5-4B (finding 4).
- **Languages.** "Multilingual" only. Neither card names EN, ES, DE or RO.
- **llama.cpp.**
  - NuExtract3 uses the same qwen35 architecture as Qwen3.5-4B, so llama.cpp support follows from Qwen3.5 support. A community GGUF with mmproj exists: about 3.4 GB at Q4_K_M plus BF16 mmproj (finding 5). I did not see a smaller or F16 mmproj.
  - That size fits only the ≥6 GB RAM tier, as a replacement candidate for MedGemma 4B, not for the 2B slot.
  - The NuExtract-2.0-2B card links to quantizations for llama.cpp, but I did not open them.
- **VAREX.** I did not verify the 90.8% vs 9.7% figure this round. The brief attributes it to NuExtract 2.0 2B against its base.

**Q2, MiniCPM-V 4.6.**
- **Licence and size.** Apache-2.0 for code and weights, so commercial use looks permitted. I saw no separate registration terms, but did not open the "Model license" link. The card says 1B params; a third-party blog title says 1.3B but could not be fetched (TLS error).
- **No numbers found.** Neither the HF card text nor the GitHub README text gives numeric OCRBench, OmniDocBench or DocVQA values. All figures are images. The only quantitative claim is "Qwen3.5-2B-level on OCRBench" (vendor-claim).
- **Phone figures.** No RAM or tok/s values in text. There are demo videos on iPhone 17 Pro Max, Redmi K70 and Huawei nova 14.
- **Runtime.** Official GGUF and llama.cpp guide.

**Q3, llama.cpp issues.**
- **#20515, #20603 and #27649 were all auto-closed as stale ("not_planned"). None was fixed.**
- #20515: AMD desktop Vulkan. Not a target-platform concern for phones or Apple; it is a concern for Windows on AMD iGPU.
- #20603: directly relevant. Qwen3.5-2B on Adreno Vulkan gives gibberish and is slower than CPU. It is consistent with llamadart 0.8.19 "fixed corrupt Qwen3.5 output on Android Vulkan" and with llamadart's CPU defaults for Qwen3.5 0.8B/2B on Android. I infer the safe Android path is CPU.
- #27649: directly relevant (Android CPU mtmd vision encode 2.7x slower after b10516). It is unconfirmed by maintainers and was not bisected. Whether llamadart 0.15.x includes the regressing commits cannot be told from the changelog (finding 16).
- **Metal.** No open GDN correctness bug. #28166 is warnings only, partly fixed by #27941. #27442 (long-context empty output) concerns the MoE variant and more than 16K tokens, which is not our use.
- **Retracted report.** #30742 (quality gap) was retracted; it was a harness error.

**Q4, litert-community VLMs.**
- **InternVL3.5-2B (about 1.61 GB):**
  - Apache-2.0; vision runs on-device.
  - Platforms: Android, iOS (Swift runtime), macOS, and Windows/Linux by the card's own statement.
  - Measured: only M4 Max, text path; S26 peak memory 859 MB.
  - Known Metal multi-image truncation bug.
- **Not fetched (budget):** the InternVL3.5-4B and Qwen2-VL-2B `.litertlm` cards. The InternVL3.5-2B card does not link them.

**Q5, Qwen3-VL-2B on llamadart 0.15.x.**
- No direct evidence either way. The llamadart changelog never names Qwen3-VL.
- Indirect evidence:
  - The unsloth Qwen3.5-4B mmproj uses the `qwen3vl_merger` projector type, and runs on current llama.cpp with only warnings (#28166). So the qwen3vl projector path is alive in mtmd, though this is shown for Qwen3.5, not the Qwen3-VL-2B checkpoint.
  - llamadart 0.15.0 fixed Windows projector loading.
  - llamadart 0.15.2 rejects images after Metal failures.
- I found no Qwen3-VL-specific regression issue in the GitHub search (qwen3vl + mmproj, 61 hits; top 8 by update date reviewed).
