## Notes per question

**Q1 — llama.cpp and llamadart today.** llamadart has moved fast since the 0.6.8 the app pins. It is now at 0.15.6 (~2026-10-21) and ships about daily (#1, #2). It is no longer only a llama.cpp wrapper: one Dart API also drives LiteRT-LM `.litertlm` models (#4). It covers what the app needs, which is mmproj multimodal input, LoRA, grammar and JSON-schema `responseFormat`, and tool calling (#5). It runs Metal, Vulkan (Windows, Linux and opt-in Android) and CUDA on Windows, but no OpenCL/Adreno path is documented, so Android GPU is weak (#8). Two behaviour changes matter for an upgrade from 0.6.8. Schemas with constraints llama.cpp cannot represent now throw instead of silently running unconstrained (#6), so the FHIR schemas may need simplifying. Windows projector loading was fixed only in 0.15.0 (#7). The bundled llama.cpp is identified only by a native pin and an upstream "v0.7.0@620d2225" reference, not a `bXXXX` tag (#3). Qwen3-VL and MedGemma are not named on the pages read (#10), so check them before upgrading. 124 issues are open (#9). Among other wrappers, flutter_gemma is discontinued and replaced by flutter_edge_ai, which itself uses llamadart for GGUF (#13, #14). Cactus has a Flutter binding (#24). The fllama and llama_cpp_dart wrappers were not checked this round.

**Q2 — Alternatives and what changed since May 2026.**
- **LiteRT-LM** (v0.18.0, Apache-2.0) is now the one credible cross-platform alternative. It covers all four targets, has vision input and GPU/NPU acceleration, and Google points MediaPipe users to it (#11, #15). Its Flutter support is "community" (#12), and it is already reachable through llamadart (#4) or flutter_edge_ai (#14). It has no documented LoRA or JSON-schema constrained decoding (#12, #17), which is a real gap for FHIR extraction. Its models are `.litertlm` builds, mostly Gemma; whether Qwen3-VL or MedGemma `.litertlm` bundles exist was not found.
- **Apple** added image input to Foundation Models at WWDC 2026, and it combines with `@Generable` guided generation (#18, #19). This is new since May. It covers only Apple platforms, with a fixed system model. Custom adapters were not verified this round. Apple also announced Core AI (iOS 27/macOS 27) as the successor to Core ML (#20).
- **Android ML Kit Prompt API** takes image plus text and has alpha structured output, but it is beta, limited to under 4000 tokens, validated for English and Korean only, and limited to Gemini Nano devices (#21, #22). Android-only, so partial.
- **ExecuTorch** is at v1.2 (April 2026) with multimodal enablement (#23, low confidence). No Flutter path was found.
- **ONNX Runtime GenAI** runs the Phi vision models but supports Qwen3-VL only through a workaround, and its Flutter wrapper is experimental (#35).
- **Cactus** has its own engine, Flutter binding and VLMs, and no Windows (#24). Its shipped quantisation scored 3% on GSM8K in an independent test (#27), and its licence was not verified.

**Q3/Q4 — Performance and comparisons.** The only independent same-model, same-device comparison found (john-rocky, iPhone 17 Pro, Gemma 4 E2B) ranks llama.cpp last on decode. It measured 38.8 tok/s for llama.cpp against 61.1 for LiteRT-LM, about 37% slower (#26). It also found lower GSM8K for llama.cpp Q4_K_M (76% vs 86%), and the official Gemma QAT GGUF would not load in llama.cpp (#27). LiteRT-LM held up best under sustained load in absolute terms (#29). On Mac, MLX beats llama.cpp by about 1.5–2x (#30). These are text-only numbers. No published benchmark compares VLM image-encode time across runtimes (#31), and that is the cost that dominates the app's document workload. The vendor numbers (#25, #33) agree in direction but are not independent.

## Leads worth chasing
- Check that llamadart 0.15.x mtmd loads Qwen3-VL-2B and the MedGemma 4B mmproj on all four targets. Read the rest of the changelog (offset 100000) and search the issue tracker for "Qwen3-VL" and "mmproj".
- Check whether `.litertlm` builds exist for Qwen3-VL or MedGemma, and whether LiteRT-LM has constrained decoding or JSON schema (look for "LiteRT-LM constrained decoding", `GemmaModelConstraintProvider` and the v0.18 release notes). The `libGemmaModelConstraintProvider.dylib` name in #16 suggests a constraint module exists.
- Check whether llamadart's LiteRT-LM backend accepts image input for generation, not only embeddings (#4, 0.15.0 note on "LiteRT-LM native CPU multimodal embeddings").
- Find out whether Apple Foundation Models in iOS/macOS 27 supports custom adapters together with image input, and its context window for document images.
- Look for any VLM image-encode benchmark (prefill on vision tokens) across llama.cpp mtmd, LiteRT-LM and MLX on phones.
- Check the Cactus licence, Nexa SDK, RunAnywhere, MLC LLM and the current fllama and llama_cpp_dart health. None were checked this round because of the budget.
- Check llama.cpp's OpenCL/Adreno backend status and whether llamadart plans to ship it.
