## Notes per question

**Q1. ExtractBench and VAREX scoring mechanics.**
- **LlamaIndex ExtractBench** is fully specified and fits a FHIR harness well (rows 2–5):
  - Hungarian alignment of records, with cost = number of mismatched subfields.
  - Absent key = null.
  - Every schema scalar counts in both precision and recall, so a correct null earns credit and a hallucinated value costs precision.
  - Micro F1 per document, then the mean over documents. That is a document-level macro average, which suits a document-clustered bootstrap.
- Two choices will hurt FHIR scoring if copied unchanged:
  - Strict numeric/string typing ("1,000" ≠ 1000), so Observation.valueQuantity needs a numeric comparator.
  - Opaque order-sensitive lists of scalars, so `coding[]` and `given[]` would need set semantics.
- The code is Apache-2.0 and reusable (row 6).
- **VAREX** uses the same Hungarian idea but with field-level EM/ANLS rather than F1. Its normalisation and null handling are underspecified in the paper; the code (Apache-2.0) would have to be read.
- VAREX's synthetic pipeline is a template for an EN/ES/DE/RO synthetic set with exact ground truth: fill templates with Faker-like values, then render to several modalities and DPIs. Its "Reverse Annotation" step uses an LLM only for schema discovery.
- VAREX already shows that document-level bootstrap CIs fail to separate models within about 0.5 point at n = 1,777 documents (row 10).

**Q2. FHIR-specific evaluators.**
- **flexpa/llm-fhir-eval** gives validity assertions (FHIR validator, FHIRPath equality), not accuracy scoring.
  - It has no licence and is barely maintained, so copy the idea, not the code.
  - The assertion pattern (validator pass rate + FHIRPath equality on key paths) is worth replicating as a separate "validity" metric next to field F1.
- **Infherno** is text→FHIR only, has no licence, and its README gives no metric. It is not usable as a harness. The EACL paper might define its metric (not retrieved).
- **FHIR Workbench**: the Note2FHIR F1 definition was not retrieved. Only the score range is known (row 15).

**Q3. Code-level scoring.**
- Partial credit by hierarchy has published precedent only for ICD: prefix-n match, ancestry-depth overlap and graded parent/chapter credit (rows 16–17).
- I found no SNOMED, LOINC or RxNorm hierarchical-distance metric used in shared-task evaluation.
- Inference, not evidence: tiered credit is a plausible design.
  - Exact code + system = 1.
  - Display text match without a code = partial.
  - SNOMED is-a ancestor within k hops = partial.
  - LOINC: same component/property, different method or scale = partial.
  - RxNorm: same ingredient (IN), different SCD/SBD = partial.
  - It must be stated as the team's own design.
- UCUM: ucum-lhc covers validation, conversion and commensurability checks, so compare quantities after converting to base units. Check its licence first (row 18).
- Dates: ExtractBench normalises to ISO before exact match (row 4). FHIR partial dates (YYYY, YYYY-MM) need precision-aware comparison; no source retrieved on this.

**Q4. Statistics.**
- Use a paired bootstrap or permutation test over documents, resampling whole documents (VAREX practice, row 10). Use the clustered or hierarchical variant when fields are nested in documents and documents are nested in patients or sources (row 20).
- Card et al. give no closed-form size. Their advice is simulation-based power analysis, with notebooks provided (row 19). The power analysis can't be done without pilot data on per-document F1 variance and inter-model correlation.
- No published "N documents to detect 3–5 F1 points" figure for extraction was found.
- Inference: run a pilot of about 30–50 documents, estimate the SD of the per-document paired F1 differences, then simulate the required N.

**Q5. On-device performance.**
- llama-bench covers only text pp/tg throughput, with repetitions, SD and depth (row 21).
- TTFT including image encoding, peak RAM and thermal behaviour need custom instrumentation. No source retrieved shows llama.cpp mtmd timing output.
- Thermal methodology from the literature (row 23):
  - Run sustained multi-minute loops.
  - Control the starting temperature.
  - Log CPU frequency and temperature per run.
  - Keep the screen off and use an external power monitor for energy.
- From a practitioner blog (unverified): iOS ProcessInfo.thermalState and Android PowerManager thermal status are coarse, lagging signals.
- MLPerf Client is PC/iPad only (row 22). Not checked: MLPerf Mobile, Geekbench AI and AI Benchmark.
