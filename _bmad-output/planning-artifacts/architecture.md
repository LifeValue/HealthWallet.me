# HealthWallet.me architecture reference

Reference for work in `lib/features/processing/`, `lib/features/capture/` and `lib/features/desktop/`. Rules every session needs are in `AGENTS.md`; this file holds the detail behind them. Verified against `eef6c7f` on 2026-10-22.

## Platforms and toolchain

- Flutter 3.47.7 via FVM (`.fvmrc`); Dart SDK `>=3.13.5 <4.0.0` (`pubspec.yaml`).
- Mobile: iOS 16.4+ (llamadart 0.15 floor), Android minSdk 24. Package name `com.techstackapps.healthwallet`.
- Android: Gradle 9.4.1, AGP 9.2.1, Kotlin 2.4.0, compileSdk 37, NDK 28.2. Code compiles to Java 11; CI runs Gradle on Temurin JDK 17. AGP 9 runs in Flutter's compatibility mode (`android.builtInKotlin=false`, `android.newDsl=false` in `android/gradle.properties`); `android/build.gradle.kts` raises plugins compiling below SDK 36 to 37 and fills in missing namespaces.
- Desktop: macOS 14+ (production; llamadart 0.15 floor) and Windows (Store-packaged MSIX). Linux is not scaffolded; `Platform.isLinux` branches are kept for a future port.

## Processing pipeline

1. **OCR**: `NativeTextRecognitionService` calls the `dev.lifevalue.healthwallet/ocr` method channel (`processing/data/data_source/platform/ocr_channel.dart`), rasterising PDF pages first at 200 dpi (`OcrProcessingHelper.pdfDpi`; at the previews' 72 dpi small print loses characters, a "D" read as "0"). Native handlers: Apple Vision in `ios/Runner/TextRecognitionHandler.swift` and `macos/Runner/AppDelegate.swift`, ML Kit in `android/app/src/main/kotlin/com/techstackapps/healthwallet/ocr/TextRecognitionHandler.kt`, `Windows.Media.Ocr` in `windows/runner/windows_ocr_plugin.cpp`. No OCR Flutter plugin, so iOS has no ML Kit pods and runs on arm64 simulators.
2. **Phase 1, text first**: `ProcessingRepository.mapBasicInfo` (`AiExtractionRepository.processMapBasicInfo`) extracts patient demographics, encounter and a primary diagnostic report. With at least 200 OCR characters it runs `AiInferenceDataSource.runTextPrompt()` (`processing/data/data_source/network/ai_inference_data_source.dart`, implemented in `ai_inference_handler.dart`) on the OCR text; `runVisionPrompt()` on the images is the fallback when that pass fails or finds no patient (no name and no identifier), or when the OCR text is shorter. Without the vision projector (the mmproj file missing, or `isVisionModelAvailable()` false after `initModel`) no images are sent: the text pass's result stands, or no patient. The session still reaches `patientExtracted`; a patient with no name and no identifier is not matched to a holder, so the review opens with empty patient fields and the note `processingNoPatientFound`.
3. **Phase 2**: `mapRemainingResources` reads the remaining resource types (medications, immunizations, allergies, vitals…) with `runVisionPrompt()` in batches when Deep Scan is on and the projector loaded, otherwise, and when vision gives nothing, with `runTextPrompt()` on the OCR text.
4. **FHIR mapping**: `ProcessingRepository` (`processing/domain/repository/`, implemented in `processing/data/repository/processing_repository_impl.dart`) maps the staged `MappingResources` (`processing/domain/entity/mapping_resources/`) to FHIR R4 and writes them through Drift.

Between OCR and phase 1, a document of a known layout is read by a layout extractor instead (below); steps 2 and 3 then don't run.

**One AI run at a time.** `mapContainerOnly`, `mapBasicInfo` and `mapRemainingResources` take turns in `ProcessingRepositoryImpl`: each starts once the runs started before it have ended. `cancelGeneration()` cancels the runs started so far (`shouldCancelGeneration` is true only inside a cancelled run, which stops at its next step) and stops the running llama.cpp generation through `LlamaEngine.cancelGeneration()`; `waitForStreamCompletion()` waits for those runs to end. In the data source a load (`initModel`), a prompt or `disposeModel` waits for a generation that is still ending, so a busy engine is never reused. **Cancel** (`onMappingCancelled`) cancels, waits and disposes the model like `_stopLocalProcessing`; until then the session is in `ProcessingState.stoppingSessionIds`, the screen shows `processingStopping` and Continue Processing and Retry are disabled. A step whose session left its status while the AI ran (cancelled, handed over, removed) stages nothing.

### Layout extractors

Documents printed by a clinic system with a fixed form are read by code: exactly, offline, without a downloaded model. The first is clearvis.io eye care (`processing/data/extractors/clearvis/`): the glasses-prescriptions PDF (one form per lens type, `PR-` serials) and the exam result (`EE-` serial), which lists the same prescriptions without serials.

- **Where it runs.** `ProcessingHandler.onMappingInitiated`, after the OCR and the empty-text exit, before the OCR patient pre-match, so every entry point (camera, PDF and image import, files shared from other apps, desktop drag-and-drop, a handover without phase-1 data) goes through it. `LayoutExtractionService` (`processing/domain/services/layout_extraction/`) holds the session's OCR text (read once per session, also by the model gate) and calls `LayoutExtractorRegistry.best`: the highest `score` ≥ 0.5, ties to the extractor registered first, every score logged in `ProcessingLogBuffer`. A recognised document is staged (patient through `_matchOrCreatePatient`, container, resources) and set to `draft`, the normal review; anything else, or a recognised document missing its date, patient name, store or patient number (the extractor returns null and logs which field, never a value), runs the AI pipeline unchanged. What every prescription form prints (patient, store, patient number) is read from each form and the reading most of them agree on is kept, so one form OCR garbled doesn't fail the document. A cancel during OCR stages nothing. The model gate is one method, `LayoutExtractionService.canProcess`, used by `SessionHandler.onSessionActivated`, `DocumentHandler.navigateToFhirMapper` and the queued-session message: it passes when the model exists or an extractor actually extracts the document (`recognise`, which prepares the pages itself and counts a failure as not recognised), so a recognised document needs no model.
- **Contract** (`layout_extractor.dart`). `id`, `version`, `score(text)` (cheap) and `extract(text)` → `LayoutExtraction`: clinic key, `MappingPatient`, clinic `MappingOrganization`, optional examiner `MappingPractitioner`, visit `MappingEncounter` and the document's resources. Extractors are deterministic (no AI, no network). Every resource they create or complete carries the `meta.tag` `http://healthwallet.me/extractor#<id>@<version>`, merged with the specialty tag. `LayoutKeys` gives the shared systems: a clinic's patient number `http://healthwallet.me/clinic/<clinicKey>/patient` (type `MR`), its document serials `…/<clinicKey>/document`, and stable ids (UUID v5) for the clinic and examiner, built from the clinic key (and the examiner's name) only, so they are recognised when read again and shared by everyone the clinic treats. Records keep the headings the document prints as their titles and the Encounter type, and the Encounter's `serviceProvider` is the clinic Organization.
- **Visit anchor.** The Encounter carries the visit key `http://healthwallet.me/visit/<extractorId>` = `<clinicKey>|<patientNumber>|<date>` (clearvis: the store's name slugged, since only the exam prints the website). `VisitReconciler` looks for it among the matched holder's Encounters: exactly one → `linkExisting` (the draft rides along with the identifiers it adds, e.g. the `EE-` serial); none or several → a new draft (several are never resolved by guessing; the user can swap with attach-to-encounter). Within the visit a VisionPrescription is the same one when its serial matches, or its lens type and every per-eye value (sphere, cylinder, axis, add) are exactly equal; any difference is a new record. A matched one is staged with `existingId`, and `completesExisting` when saving fills something; its form (and a linked visit's) is shown locked, with a note, since saving never changes its values. The clinic and examiner already in the wallet (same stable id) are not staged again.
- **Completion** (`RecordCompletion`). At save a matched record is read again and only fields it leaves empty are filled (serial, encounter, follow-up extension, per-eye values, a missing eye); a value is never changed. The one replace is the placeholder prescriber: a prescription without an examiner gets a display-only reference to the clinic marked with the extension `…/StructureDefinition/placeholder`, which the examiner from the prescriptions document replaces. A linked visit gets only its missing identifiers. When the person, the visit and every record already hold everything (`ProcessingSession.isAlreadyInWallet`, shown in the review), Save writes nothing: no record, no Patient fill, no DocumentReference.
- **People.** `HolderService.matchScanned` passes the scanned identifier's system; a scan with a system matches only a stored identifier of that system, and `HolderMatcher` never treats two clinic-scoped numbers of different clinics as one identity (even when both rows were typed in the app), so two clinics' `PA-00001` are two people. A scan without a system (the AI path) never matches a clinic-scoped number, and the OCR pre-match skips them.
- **VisionPrescription** is a main record type (`FhirType.VisionPrescription`, Home category "Vision Prescriptions", classified Ophthalmology), shown with a per-eye table (`records/presentation/widgets/vision_prescription_table.dart`) on the record page and both desktop panels. In the review its lens values are an editable grid turned to fit a phone (one row per value, a field per eye, `MappingVisionPrescription.lensRows`), with plain labels (Strength, Astigmatism, Angle, Reading add) and checks (dioptres in quarter steps up to ±30, angles 0–180); the date, next check-up and prescriber are its other fields. A row that `fhir_r4` can't parse (missing `status`, `created`, `patient`, `prescriber` or a lens `product`/`eye`) is listed as a generic resource; app versions without the type do the same. The AI never outputs it.

Adding a layout: implement `LayoutExtractor` under `processing/data/extractors/<layout>/`, return null when a required field is missing, use `LayoutKeys` for the clinic key, visit key, systems and stable ids, add one entry to the list in `RegisterModule.layoutExtractorRegistry` (`lib/core/di/register_module.dart`), and add tests with de-identified OCR fixtures (Apple Vision `.accurate` output, pages at 200 dpi; rule in `tool/extraction_bench/README.md`) plus the no-false-match check against every synthetic benchmark document (`test/features/processing/layout_extraction/`). Nothing else changes: pipeline, review, database and other extractors stay as they are.

### Output modes

`ExtractionOutputMode` (`processing/domain/entity/extraction_output_mode.dart`), read from the `aiOutputMode` pref on every platform and passed by `ProcessingHandler` to `mapContainerOnly`, `mapBasicInfo` and `mapRemainingResources` like the other AI tuning prefs. Unset or unknown → `ExtractionOutputMode.defaultMode`, which is `schema` since the 2026-10-26 measurement (`tool/extraction_bench/README.md`, "Output-mode measurement").

| Mode          | Each generation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `grammar`     | `GbnfGrammars.jsonArray`: any JSON array of objects; prompts describe `resourceType`-tagged objects                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `schema`      | A flat JSON schema per phase as llamadart `responseFormat` (no grammar): phase 1 one object (patient fields, `documentTitle`, `documentDate`, `conclusion`, `documentCategory` enum), container-only the document fields, phase 2 one object of arrays per category (`lab_report`: observations, practitioners, organizations; `visit`: conditions, medications, procedures, allergies, vitalSigns, practitioners, organizations; anything else the union). Enums for closed sets, dates as `^([0-9]{4}(-[0-9]{2}(-[0-9]{2})?)?)?$` (llamadart's pattern subset has no `\d`), `maxItems` on every array, `additionalProperties: false` |
| `schemaDraft` | An unconstrained draft call (≤ 384 tokens, same modality as the step), then the `schema` call text-only with the draft and the OCR text in the prompt (text context ≥ 4096). A failed draft leaves the constrained call without one                                                                                                                                                                                                                                                                                                                                                                                                    |

`processing/data/model/structured_output/extraction_schemas.dart` holds the schemas, the shape text the prompts show (llama.cpp does not inject the schema into the prompt) and the mappers from the schema output back to the legacy `resourceType` maps, so `MappingResource.fromJson`, the dedupe and skip rules, the review UI, sync and the DB are the same in every mode. Output cut off mid-JSON is salvaged up to the last complete array item; unusable phase-2 output gives no resources, unusable phase-1 output takes the vision fallback as before. Every schema is checked with llamadart's `LlamaStructuredOutput.jsonValueSchema` in `test/features/processing/extraction_schemas_test.dart`.

Shared by all modes: the basic-info prompts and `PatientPostProcessor`'s default label take their country from the document (`CountryIdentifier.forDocument`: identifier names and field labels scored in the OCR text, the phone locale only when nothing or a tie matches), and lab-report prompts and their few-shot example no longer offer Condition. Phase 2 OCR is per page (`OcrPages`): lines of 8+ characters printed on every page (all but one from 3 pages up; letterhead, patient block, footer) are kept on the first page only. Each vision batch (`AiModelConfig.visionPagesPerBatch` pages: 2, or 1 for Qwen3.5-4B, whose ~840-token pages overflow the 4096 vision context two at a time with a long lab answer) gets its own pages' OCR, up to 2000 characters, and the few-shot example; in `schemaDraft` the vision draft call gets that OCR only (no example, no shape). Text calls (the fallback, and the constrained pass in `schemaDraft`) load at a 4096 context, or the smaller text context when 4096 does not fit in memory, and split the pages into chunks of (context − 1000 prompt − 1500 answer tokens [− 384 draft]) × 2 characters (3192 at 4096, at least 800), one constrained call per chunk, outputs merged and deduplicated by type and name. The earlier fixed 2000-character head (HM-181, a crash workaround at a 2048 context) left ~300 tokens for the answer and cut a 4-page lab report after its second test. `ObservationOcrValidator` adds or corrects an observation from an OCR line only when its unit is a lab unit (`%`, an SI-prefixed `g`/`mol`/`L`/`IU`/`UI`/`U`/…, `x10^n`, with `/denominators`) and its name is not a range row (ending in a dash), a page footer, or a phone, address or code label. `GenerationStats.finishReason` (`length` = truncated) is recorded per generation.

`fhir_r4_validation` (probe, 2026-10-26): not used. 0.14 needs `fhir_r4 ^0.14` (the app and `fhir_ips_export` are on 0.6), validates against an R4B (4.3.0) model, and ships no definitions: offline, with its default cache, every resource fails with "No StructureDefinition found". With the HL7 R4 or R4B `definitions.json` loaded into a cache it still needed two workarounds (complex types are looked up by bare name, and a binding to a terminology.hl7.org value set outside the core package throws and aborts the run), and then 32 of 40 `toFhirResource` samples (4 per type, from benchmark runs) failed on validator-internal errors on Reference, Period, Quantity and ContactPoint ("Element type or path is missing", "Context is null for <invariant>"), every type but Patient and Practitioner. 6 came out valid (2 Patients, 4 Practitioners); the other 2 Patients carry the one real defect it found, a model-written `gender` of `Female`, which the required administrative-gender binding rejects and the `schema` mode's gender enum rules out.

### Extraction benchmark

`tool/extraction_bench/` measures the pipeline's document→FHIR accuracy; usage, dataset layout, scoring and the de-identification rule for real documents are in `tool/extraction_bench/README.md`.

- `bench.dart` (pure Dart, `fvm dart run tool/extraction_bench/bench.dart`): `generate` writes seeded synthetic lab reports and discharge letters (EN/ES/DE/RO) as PDF plus a gold FHIR R4 Bundle; `score` matches predicted to gold resources per type (Hungarian), scores fields with FHIR-aware comparators (UCUM, partial dates, code tiers) and reports per-document F1 with document-level bootstrap CIs per stratum; `compare` runs a paired bootstrap between two runs; `oracle` writes gold-as-prediction as a sanity check.
- `integration_test/extraction_bench_test.dart` runs the production classes on a desktop or device (`--dart-define=BENCH_MODEL=<variant>`), reading `<documents>/extraction_bench/dataset/` and writing `<documents>/extraction_bench/results/<runId>/predictions.jsonl`. It mirrors `ProcessingHandler` (phase 1, `docCategory` from the container, phase 2) but skips the OCR pre-match against existing patients.
- The only production seam is `AiInferenceDataSource.lastGenerationStats` (`GenerationStats`: prompt/completion tokens, time to first token, prompt eval, duration), reset at the start of every `runVisionPrompt` / `runTextPrompt`. Image-encode time is read from llama.cpp's mtmd log lines, which only the runner subscribes to through `LlamaLogging.configure`.
- Datasets, results, models and real documents are never committed; keep them under `build/` or outside the repository.

## Database

`lib/core/data/local/app_database.dart`, `schemaVersion` 14, opened on a background isolate (`NativeDatabase.createInBackground`). Tables: `FhirResource`, `Sources`, `RecordNotes`, `ProcessingSessions`, `SyncOutbox`. v1→8 migrate with drift `stepByStep` (there is no v4; `from3To5` covers it). v8→9 (per-patient wallet sources), v9→10 (sync triggers), v10→11, v11→12 (note keys) and v12→13 (sync outbox, millisecond triggers) and v13→14 (`sources.holder_id`) are hand-written in `onUpgrade`. Snapshots for v1–3 and v5–14 are in `drift_schemas/my_database/`, generated test schemas in `test/drift/my_database/generated/`, tests in `test/drift/my_database/migration_test.dart`.

Triggers set `updated_at` in milliseconds on insert and on any update that leaves it unchanged, never lower than the row's previous stamp (an edit after receiving a row stamped by a clock that runs ahead still wins); filling in a note's `uuid` (below) doesn't count as an update. On the three synced tables, triggers also log every insert and update in `sync_outbox` (`synced_table`, `row_key`), which is what the desktop sync sends; Dart code doesn't set `updated_at` on these tables.

Row ids: a Fasten resource is stored under its FHIR id, unless that id already belongs to a resource of another source or type; then it is `sourceId/type/id` (`SyncLocalDataSourceImpl.cacheFhirResources`). Notes have a local integer `id` and a `uuid` that identifies them on every device: a v4 UUID for new notes, `legacy-<id>` for notes from before v12 or from an app version without the column (a trigger fills it in). `record_notes.source_id` references `sources`, with foreign keys on: delete notes before their source.

Holders: `sources.holder_id` says whose records a source holds; sources with the same holder are one person in the wallet. It syncs with the rest of the row, so the phone and the desktop agree. `HolderLinkingService` (`lib/features/holders/`) links every source without a holder at start-up on both ends, which also fills the column after the upgrade to v14, and again whenever the holders are read: a source joins a person through its Patient rows, the patient a `wallet-<id>` source was made for, or the patients its records refer to; Patient rows join when `HolderMatcher` matches them (national identifier, then full name and birth date, a record number only within its system). Someone who matches no one is never placed by guessing: when the wallet already has someone, `HolderQuestionListener` asks the user whose records they are, and the newcomer's sources stay unlinked (out of every view) until they answer; when it has no one (the demo person aside), the newcomer becomes a holder. On the first run after the upgrade, the people found are taken as the app showed them, each a holder, except next to an untouched default holder, which is the user: the others are asked about. Demo data is always its own person. Linking never moves a source to another holder. Holders whose patients share an identifier (the same national number, or the same record number in one system; an ID typed in the app counts by its value, since its system comes from the device's region) are merged on every read, into the smallest holder id, so two devices that each linked their own copy of someone before syncing end up with the same single holder. Name and birth date alone don't merge two holders. A new holder's id is derived from its records, so devices with the same records give the same id. An older peer drops the column, and its rows don't clear it (the upsert writes only the columns sent).

`HolderService` is the read side: `load()` gives the holders (each with its sources, its Patient rows and the row shown for it, its own wallet Patient when there is one) and the open questions; `PatientBloc`, Home, attach-to-encounter and processing read people from it. It is also the one place a holder's wallet source is found or made (`walletSourceOf`, `wallet-<holderId>` for a new one), so scans, attachments and edits of one person land in one wallet source. A scanned patient is matched to a holder by identifier value or by name with full birth date; with only the unnamed default holder in the wallet, it is proposed.

The default patient ("Health Wallet Holder") is stored under a random row id on each install (the save path keys rows by FHIR id, which is a UUID), in the shared source `wallet-default_patient`, so after a sync a person can hold one copy per device. It is recognised by its content (that name and the identifier `default_patient`), and the row shown for a person, which the patient card, the edit form, Home and the wallet pass all use and which edits and scans write to, is never an untouched copy when the person has a row with details.

`HolderSelection` owns whose records the app shows: the selected holder (`selected_holder_id`; the Patient row id older versions kept in `selected_patient_id` is read once as its holder) and an optional filter on one of their sources (`home_selected_source_id`). Its `HolderScope` gives the sources to read (the filter, or all the person's sources; none until the people are read; every source when the wallet has no one) and the Patient row to show. `refresh()` reads the people again and keeps the selection while it still exists; `PatientPatientsLoaded` is how screens ask for it after a sync, scan, edit, answer or delete. `PatientBloc` and `HomeBloc` follow `HolderSelection.changes`; Records reads the scope from `HomeState.scope`. The wallet pass takes all the person's sources and their own row whatever the filter, so a pass already in Wallet keeps its serial; IPS export takes what Home shows.

Sources: a provider fetch (`SyncLocalDataSource.cacheProviderSources`) adds new sources with the provider's name and updates only the provider's own fields of known ones, so the user's name for a source, its holder and its delete survive; records of a deleted source aren't stored again. A wallet source stores no label and is shown under its person's current name (`sourceDisplayName`). Home can remove a provider's source and the demo data (through `clearDemoData`), never a wallet source, which holds the person's own Patient row.

Deleting records goes through `RecordsRepositoryImpl._deleteRecords`: it also deletes their notes and the DocumentReferences attached only to them (`context.related`). It removes no file: attachment files stay until the tombstones are purged after 30 days (see **Sync**, item 5), so undo and restore find them.

## Mobile ↔ desktop communication

Mobile is the client, desktop the server; one phone is paired with one desktop. They talk over TCP or, between an iPhone and a Mac, MultipeerConnectivity (MPC, from `airdrop`), with the same protocol on both (`link_protocol.dart`, version 2). Both apps must run version 2; an older peer is told to update, not half-served.

### Pairing

The desktop makes a pairing on first start (`DevicePairing`: `deviceId` (UUID v4), `deviceName`, `pairingKey` (32 random bytes, base64url), `lastIp`, `lastPort`). Its QR code (`DevicePairing.toQrPayload`) carries `v`, `device_id`, `device_name`, `pairing_key`, `ip`, `port` and `os`; the phone checks it with `DevicePairing.parseQr` (version, a 32-byte key, a valid port). Keys are stored in the platform's secret store (`SecretStore`: Keychain this-device-only, Android Keystore, Windows DPAPI; on macOS the legacy keychain, which needs no entitlement), the rest of the pairing in SharedPreferences (`device_pairing`).

The first phone to complete a handshake becomes the paired phone (`peerDeviceId`). The desktop then gives it a new key over the session (`pairing.rekey` / `pairing.rekey_ack`), accepting both keys until the phone uses the new one, so the QR code that was shown stops working. Once a phone is paired the desktop shows its name, not the QR code; "New QR code" makes a new pairing. Another phone that holds the current key (and proves it) waits until the desktop's user accepts or declines it; accepted, it replaces the paired phone.

### Discovery (mobile, `communication_bloc.dart`)

1. **Saved address**: `lastIp:lastPort`, saved only after a handshake there succeeded.
2. **Bonjour + SSDP**: `_healthwallet._tcp` with a TXT attribute `t` (a token derived from the key and the desktop id, `discoveryToken`), resolved explicitly, every answer within 3 s (a desktop that restarted can leave its old entry, on a dead port, next to the new one); SSDP (not on iOS, which needs a multicast entitlement Apple grants on request) filtered by the desktop id, using the answer's source address. Results are candidates only.
3. **MPC**: the Mac advertises the token in `discoveryInfo` and accepts only an invitation carrying it, one peer at a time, and stops advertising while connected; the iPhone invites only that Mac and stops browsing when the attempt times out.

Every candidate must pass the handshake, which checks the desktop's id and proof. A desktop that answers "unknown key" (a new QR code was made), declines the phone or speaks another version ends the attempt with that reason and no retry. An attempt (saved address, discovery, every candidate, MPC) still running after 60 s (`connectionAttemptTimeout`) is given up, whatever step it waits on, and tries nothing more. After any other failure, or that one, the phone retries with a doubling delay (3 s, 5 attempts), then waits for the app to come back to the foreground or for Reconnect. The pairing is never cleared by itself. A desktop user's Disconnect (`kill` with reason `user`) keeps the phone disconnected; a desktop quitting (`shutdown`) doesn't.

The desktop listens on every interface (port 49152 or a free one) and checks its address every 30 s, updating the QR code and the advertisements; without a usable address it says so instead of showing a QR code. It holds up to 8 sockets; each must complete the handshake within 15 s, and the newest verified session replaces the previous one, so a phone that reconnects after a drop is never locked out by its own half-open socket.

| Mobile \ Desktop | macOS     | Windows |
| ---------------- | --------- | ------- |
| iOS              | MPC + TCP | TCP     |
| Android          | TCP       | TCP     |

### Wire format

TCP frames are `[4-byte big-endian length][body]`; MPC carries bodies in pieces of at most 60 KiB (`[1 = last][bytes]`). A body starts with a kind byte: `0x00` alone (the desktop doesn't know the phone's key), `0x01` handshake (`[12-byte nonce][AES-256-GCM]` under the pairing key) or `0x02` session (`[8-byte counter][AES-256-GCM]`, the counter being the nonce, under a key for this session and direction). A session frame must carry the next counter, so frames can't be replayed, reordered or reflected. Frames are capped at 64 KiB until the handshake completes and at 16 MiB after.

Handshake: the phone sends `hello` (`v`, its device id and name, a 16-byte nonce); the desktop answers `ack` (`v`, its id and name, its nonce, an HMAC proof over both nonces and ids under the pairing key); the phone checks the id and the proof and sends `confirm` (its own proof). Both derive the session keys with HKDF-SHA256 from the pairing key and both nonces. The desktop then sends `ready`, or a session `ack` while its user decides on an unknown phone, or `reject` (`version`, `declined`).

The decrypted payload starts with a type byte:

| Code | Type      | Meaning                                                                 |
| ---- | --------- | ----------------------------------------------------------------------- |
| 0x01 | `hello`   | Handshake, phone → desktop                                              |
| 0x02 | `ack`     | Handshake answer; in a session: waiting for the desktop user's decision |
| 0x03 | `ping`    | Phone keep-alive every 10 s                                             |
| 0x04 | `pong`    | Reply to ping                                                           |
| 0x05 | `data`    | Application message, JSON `{type, payload}`, routed by `MessageRouter`  |
| 0x06 | `confirm` | Handshake, the phone's proof                                            |
| 0x07 | `reject`  | Handshake refused: `version` or `declined`                              |
| 0x08 | `ready`   | The desktop accepted the session                                        |
| 0xFF | `kill`    | End of session, JSON `{reason}`: `user` or `shutdown`                   |

Either side drops a link it heard nothing from for 25 s (phone) or 35 s (desktop); any frame counts, so a long transfer never trips it. Sending without a verified session throws `LinkNotConnectedException`.

### Application messages

**LWW sync** (`desktop/lww_sync/`), all handled in one queue by `LwwSyncBloc`:

| Type                | Direction | Meaning                                                                                                   |
| ------------------- | --------- | --------------------------------------------------------------------------------------------------------- |
| `sync.batch`        | both      | Up to 200 rows (about 2 MB) from the outbox, by table (`SyncBatch`: `id`, `deviceId`, `tables`, `more`)   |
| `sync.ack`          | both      | `{id, ok}` after the batch was applied in one transaction                                                 |
| `sync.digest`       | both      | Per table, the row count and a SHA-256 of every key with its `updated_at`; `reply` marks the answer      |
| `sync.manifest`     | both      | For a table whose digests differ: every key with its `updated_at`                                         |
| `sync.file_request` | both      | Attachment paths the receiver lacks                                                                       |
| `sync.file_chunk`   | both      | `{path, offset, total, data}`, 256 KiB of base64 at a time                                                |
| `sync.file_missing` | both      | The requested file can't be sent                                                                          |

Sending: one batch at a time, the next after the `sync.ack`. The outbox position the peer acknowledged (`ackedSeq`, per peer in `lww_sync_state`) is the only thing that moves, so nothing is lost to a dropped link, a crash or a rejected write, and nothing depends on either device's clock. A batch not acknowledged within 60 s is sent again on the next trigger. The receiver applies a batch in one transaction (row by row when one row fails), and the writes don't go back into the outbox. `more` says the sender's outbox held further changes when it sent the batch; the receiver reloads its lists 1 s after the last batch of a run, or 10 s after one marked `more` if nothing follows (a dropped link, or only deleted rows left). A batch without `more`, from an older version, counts as the last one.

Reconciliation: on connecting both sides send `sync.digest`; for each table that differs they exchange `sync.manifest` once per connection and queue the rows the other lacks or holds older. After a round of sending, the sender compares digests again; "in sync" means connected, nothing waiting, nothing in flight and the digests matching. A new peer (another desktop, a new phone) starts with a fresh outbox position and reconciles. A desktop restore keeps the position: it writes every restored and superseded row through the outbox with a fresh stamp (see **Backup**), so it reaches the phone like any edit, and the digest on the next connect covers a phone that was offline.

Deletes travel as `deleted_at` tombstones:

1. A user delete of a `fhir_resource`, `sources` or `record_notes` row runs `UPDATE … SET deleted_at = :nowMs, updated_at = :nowMs`, in milliseconds through raw SQL, never through a drift `DateTime` (drift stores seconds). Already tombstoned rows are left as they are. Deleting a record or a source also tombstones the notes of the deleted records; clearing demo data and replacing a scan's DocumentReferences tombstone too. Deleting a record also tombstones the documents attached only to it. No record or attachment delete, local or received through sync, removes a file: a deleted record keeps its attachment files until its tombstone is purged (item 5). The statements live in one place, the `SoftDelete` extension on `AppDatabase` (`lib/core/data/local/soft_delete.dart`); repositories and data sources call it, and their delete methods (`RecordsRepository.deleteResource`, `deleteResourcesByIds`, `deleteResourceWithRelated`, `deleteRecordNote`, `clearDemoData`, `SyncLocalDataSource.deleteSource`, `DocumentReferenceService.replaceSessionDocuments`) are soft.
2. Tombstones travel like any edit: the update that sets `deleted_at` is logged in the outbox, and manifests and digests include tombstoned rows. LWW per row decides: the newer `updated_at` wins, so a later edit on the other device resurrects the row, and reconciliation does not bring a deleted row back. Files are requested and served only for live DocumentReferences.
3. Every UI and export read excludes `deleted_at IS NOT NULL` (records, related records, references, search, notes, sources, DocumentReferences of a scan). Row counts already did.
4. Every save or insert of a row clears `deleted_at` (upserts write `deleted_at = NULL`, and the `INSERT OR REPLACE` paths replace the whole row). The demo and wallet source rows leave `updated_at` to the trigger rather than drift (which stores seconds). The trigger stamps in milliseconds and never moves a row's stamp back, so a re-created row beats its tombstone. In-place updates of a single column (raw JSON, specialty, note text, encounter link) leave `deleted_at` as it is, so they never resurrect a row.
5. `cleanupTombstones` (on `LwwSyncInitialised`) hard-deletes tombstones older than 30 days: notes first, then records, then sources, and a source stays while a newer note still points at it (`record_notes.source_id` is a foreign key the app enforces). A device offline for longer than that can bring the row back; this limit is accepted. The purge reads the `file://` urls of the records it removes in the same transaction as the `DELETE`; after it commits, `AttachmentFileCleaner.deleteUnreferenced` (`lib/core/services/attachment_file_cleaner.dart`) deletes each of those files that no remaining row (live or tombstoned `fhir_resource`, or `processing_sessions.file_paths` and `resources`) refers to and that is more than 1 hour old (a younger one may be a new file of the same name whose row isn't committed yet; it is left to the sweep), then `sweep()` starts in the background. On Windows the purge also deletes, by the same rules, a purged record's absolute url whose file is top-level in a `LegacyAttachmentFolders` root (the Documents folder older versions saved attachments to); the sweep never enters it. The sweep never deletes a leftover file directly: it moves every top-level file in Documents that no row refers to and that is more than 7 days old by `max(modified, changed)` into the hidden quarantine folder `Documents/.trash/` (a free name on a clash, its modified time set to now on arrival), then deletes the top-level regular files of `.trash/` older than 30 days (no symlinks, nothing in its subfolders). Every copy into Documents sets its modified time, so a file whose row isn't written yet is kept. `.trash` is a dot-folder: the sweep's and the purge's listings skip it, and `AttachmentSyncService.resolveFile` serves nothing under a dot-name in Documents, so sync and backups never send or copy a quarantined file. Only the purge deletes record files directly. Both follow the same rules: only top-level regular files of `PathResolver.getDocumentsPath()` (no symlink, dot-file, `db.sqlite*`, `*.log`, `*.db`, nothing in a subfolder; nothing when the directory itself is a link), references found through `AttachmentReferences` (an unreadable row is matched as raw text, so the file is kept), each file checked and deleted inside its own `AppDatabase.transaction` so a sync write can't interleave (`isReferenced` pre-filters rows in SQL on the name and decodes only those), every delete, move and failure logged with a short hash instead of the file name, and counts at info level. Neither runs on Linux, where Documents is the user's own folder. It is the only code that deletes record attachment files; scan sessions delete their own working files in `imports/` (`ProcessingRepositoryImpl.deleteProcessingSession`). Accepted limit: files of purged records inside a subfolder are never deleted.

Reset (`AppDataResetService`), `deleteAllFhirResources` and `deleteAllSources` stay local hard wipes. A backup restore doesn't: rows added since the backup become tombstones (see **Backup**).

Conflicts: the later `updated_at` wins; on a tie the row from the larger device id wins, the same answer on both sides; a row identical to the local one is not written. Incoming columns are kept only if the table has them. A local `DocumentReference` with a missing attachment loses to the incoming row, and an incoming one keeps the local file of an attachment that it names differently.

Files never travel inside rows. The receiver asks for the attachments of the rows it applied (and, on connecting, for every missing one); the sender serves only paths a live `DocumentReference` refers to, at most 200 MB, in chunks, outside the event queue. A received file gets a free name in Documents (never replacing a file or the database), and the record is repointed to it without counting as an edit.

The archived PRD (FR35, NFR14) asked for soft-delete propagation with 30-day tombstone cleanup; the tombstone rules above implement it.

**Backup** (`desktop/backup/`): desktop backups in the chosen folder, by default `~/Documents/HealthWallet/Backups/` (`USERPROFILE` on Windows; on macOS a subfolder of the sandbox Documents, which no file sweep enters). `BackupService` (`backup_service.dart`) writes, lists, restores and deletes them.

Format 2, one backup:

- `<name>.db`: `VACUUM INTO` copy of the database.
- `<name>.files/`: one copy of every attachment file a `fhir_resource` row (live or tombstoned) refers to, found through `AttachmentReferences` (`lib/core/services/attachment_references.dart`: every `file://` url in `resource_raw`, basenames split on `/` and `\`, compared raw and decoded, ignoring case). Files resolve inside `PathResolver.getDocumentsPath()` (as `AttachmentSyncService.resolveFile`), plus top-level files of the Windows Documents root, where older versions saved attachments. Same-named files get free names. Scan-session files (`imports/`) are not backed up.
- `<name>.db.meta.json`, written last (through a `.tmp` and a rename) as the commit marker: `BackupEntry` with `formatVersion: 2`, `files: [{name, sourcePaths, sha256, size}]` (`sourcePaths` are the decoded paths the rows store), `missing: [url]` (files not on the device) and `isSafetyCopy`. A failed backup removes its `.db`, `.files/` and metadata. Metadata without `formatVersion` is a database-only backup (format 1); older app versions list format 2 and restore its rows only.

Listing reads every `*.db.meta.json` and takes the `.db` and `.files/` paths from where the metadata is, not from the stored `filePath`, so a moved folder still works; unreadable metadata is logged and skipped. The display name is kept as typed; the file name keeps letters of any script, digits and `-._,`, with `:` as `.`. Hashes (SHA-256) are streamed. Deleting removes the metadata first, then the `.db` and `.files/`.

Restore (`restoreFromFile`) makes the backup the current state on the desktop and, through sync, on the phone:

1. Leftover `Documents/.restore-*` folders are removed (also at start-up, `cleanUpOnStartup`), and the `.db` checksum is checked against the metadata.
2. Format 2 files are copied into `Documents/.restore-<id>/`, hashed and moved into Documents with `setLastModified(now)`. No current file is deleted or overwritten: a file already found by the restored rows, or of the same name, with the same hash is reused; one with other content keeps its name and the backup's file goes under a free name. A missing or damaged file is counted (`RestoreResult.filesNotRestored`) and the rest goes on. A format 1 backup adds no file and keeps every current one.
3. In one transaction, for `fhir_resource`, `sources` and `record_notes`, with `S = MAX(now, max(updated_at) over current and backup rows + 1)`: current rows whose key isn't in the backup (`id`; `COALESCE(uuid, 'legacy-' || id)` for notes, the same on both sides) go to TEMP tables; every table is emptied children first; the backup's rows are inserted with `updated_at = S`, their tombstones with `deleted_at = S` (so the 30-day purge doesn't drop them before they reach the phone), and missing `updated_at`, `deleted_at` or `uuid` columns of an old backup read as `S`, `NULL` and `'legacy-' || id`; the TEMP rows go back as tombstones with `deleted_at = updated_at = MAX(S, updated_at + 1)` and their `resource_raw`, notes without their per-device `id`. Plain INSERTs, so the insert trigger leaves `S`; the outbox triggers queue every row. Attachment urls of restored rows that must point at a renamed file are rewritten in the same transaction and keep `S`. `sync_outbox` is never restored; `processing_sessions` and other local tables are replaced by the backup's.
4. A failure before or inside the transaction leaves the database as it was and removes the files the restore added and the staging folder; `restoreFromFile` throws only then. After the commit the caller sends `LwwSyncEvent.localChanged()` and doesn't call `resetPeerState`, which would prune the outbox the restore filled. The phone then applies the rows (they win on `S`, even against a phone clock that runs ahead) and requests the restored files as for any missing attachment.

Before a restore the backup bloc saves a safety copy, "Before restore {date}" with files (`createSnapshot(isSafetyCopy: true, keepId: <the backup being restored>)`, never streamed to the phone). It is the undo. Safety copies older than 30 days are deleted at start-up and after each backup (`deleteExpiredSafetyCopies`), except the `keepId` one, so restoring an old safety copy never deletes it first; user backups are never deleted. A referenced file that can't be read (locked, no permission) is listed in `missing` and doesn't stop the backup. Deleting a backup whose metadata can't be removed leaves it whole.

While the safety copy and the restore run, `LwwSyncBloc.pauseApplying()` holds the whole LWW event queue, not only batches: a received batch waits before it is applied, and the acks, digests, file requests and connection changes queued behind it wait too, until `resumeApplying()`. Nothing is refused; a phone ack timeout and resend is harmless because applying is idempotent.

The phone fetches restored files only for DocumentReference attachments (`sync.file_request` is served for live DocumentReferences only). Media and other attachments a restore brings back stay on the desktop.

| Type              | Direction         | Meaning                              |
| ----------------- | ----------------- | ------------------------------------ |
| `backup.request`  | mobile → desktop  | Take a snapshot                      |
| `backup.status`   | desktop → mobile  | Readiness                            |
| `backup.meta`     | sender → receiver | Size, SHA-256 checksum, chunk count  |
| `backup.chunk`    | sender → receiver | 64 KB chunk, base64                  |
| `backup.complete` | sender → receiver | Done; receiver verifies the checksum |
| `backup.error`    | either            | Failure                              |

`backup_bloc.dart` also sends `backup_start`, `backup_chunk` and `backup_complete`; nothing listens for them. The phone asks for a backup (`PhoneBackupRequested`) only once its changes were acknowledged, so the snapshot holds them.

**Handover** (`desktop/handover/`): the phone sends a document to the desktop, which runs the AI; the draft can then be reviewed and saved on either device, and the first save wins. On the phone `HandoverSenderService` (transfer, outbox) and `PhoneHandoverBloc` (started in `main.dart`); on the desktop `HandoverService` (receive, outbox) and `HandoverBloc` (started in `main_desktop.dart`). Messages are `data` frames (`HandoverMessage` in `domain/entity/handover_protocol.dart`), each with `session_id`: the phone's processing session id, which the desktop's session takes too (`DocumentImported.sessionId`), so both ends always speak about the same session.

| Type               | Direction        | Meaning                                                                                         |
| ------------------ | ---------------- | ----------------------------------------------------------------------------------------------- |
| `handover.offer`   | phone → desktop  | `v` (2), `files` (`name`, `size`), optional `phase1_data` (the phone's patient step)             |
| `handover.accept`  | desktop → phone  | Ready for the files                                                                             |
| `handover.reject`  | desktop → phone  | `reason`: `version` (another handover version), `too_large` (over 200 MB), `failed`             |
| `handover.chunk`   | phone → desktop  | `index`, `offset`, `data`: 256 KiB of a file, base64, in order                                  |
| `handover.progress`| desktop → phone  | Processing `progress`, 0 to 1                                                                   |
| `handover.result`  | desktop → phone  | `draft`: the staged patient, visit or report, and records, ids included (`HandoverDraft`)       |
| `handover.failed`  | desktop → phone  | `reason`: `model_not_found`, `timeout`, `failed`                                                |
| `handover.saved`   | either           | The records were saved on the sender; the other device drops its draft                          |
| `handover.cancel`  | either           | The phone took the document back, or the desktop's user deleted it                              |
| `handover.ack`     | either           | `type` of the `result`, `failed`, `saved` or `cancel` received                                  |

`result`, `failed`, `saved` and `cancel` wait in an outbox (`HandoverOutbox`, in preferences) until the other device acknowledges them, and are sent again on every connection and every 30 s while connected; receiving one twice changes nothing. A device acknowledges a message about a session it no longer has and drops it.

- **Phone.** `PhoneHandoverSendRequested` checks the files, sends the offer (listening for the answer first), and the files in chunks; a missing file, a drop, a cancel, a refusal or no answer within 30 s (an older desktop never answers) ends the transfer with a `HandoverFailure`, never an exception. Once every byte arrived the session becomes `ProcessingStatus.handedOver`: local processing stops, the queue skips it, and the processing screen offers "Process on this phone instead" (`handover.cancel`). The desktop's draft makes it a `draft` again (`HandoverDraftReceived`); it keeps its origin, so it stays in its Scan or Import tab, and the sessions the desktop also holds are listed in the `handover_sessions_phone` preference. A failure shows only on the session it belongs to (`Failure.sessionId`), and over a draft only a failed save; a failure or a delete on the desktop returns it as it was (`HandoverReturned`); a save on the desktop removes it (`SessionSavedElsewhere`). Saving or deleting it on the phone tells the desktop.
- **Desktop.** Files are assembled by index and offset in a temporary folder, a folder per page, under the document's own name without the phone's unique suffix (`safeFileName`), so processing's stored copy, and the title read from it, carry that name (a gap or a repeat fails the transfer, 60 s without a chunk times it out) and deleted once processing has its own copies. The session runs through to its draft without anyone at the desktop: with the phone's patient step it continues from it, otherwise it starts from the beginning; while another session processes it waits its turn (`ProcessingBloc.startNextPendingSession` continues handovers first). A failure of that session (`Failure.sessionId`) is reported; the queue doesn't retry a failed handover until the user does. Its draft is sent once (`handover_reported_desktop`), a save there sends `saved` (`Success.sessionId`), a delete sends `cancel`. The Handover tab shows transfers while they arrive and the handover sessions.
- **Saving on both.** A session's records keep the draft's ids and its documents get ids from the session (`DocumentReferenceService.sessionDocumentId`), so saving the same handover on both devices while apart writes the same rows, which the LWW sync merges.

**Tray** (`desktop/tray/`): `TrayService` owns the macOS/Windows tray icon and menu, `WindowLifecycleService` minimise-to-tray and restore, `TrayBloc` reflects connection and sync state.

## Proximity sharing encryption

Phone-to-phone shares (`share_records/`) are end-to-end encrypted in the app, on top of whatever the `airdrop` transport provides (an Android hotspot between iOS and Android, Wi-Fi Direct between Androids, MPC between iPhones). Crypto is in `data/crypto/share_crypto.dart`, the exchange in `data/service/secure_share_session.dart`, both on pointycastle: P-256 ECDH, HKDF-SHA256, AES-256-GCM.

1. The sender encrypts the payload JSON with a random 32-byte key K and transfers the envelope `"HWSE" | version 1 | SHA-256(sender public key) | nonce (12) | ciphertext + tag`, with the bytes before the nonce as associated data. The file holds no plaintext and not the sender's key.
2. After the transfer, over `airdrop` session messages (signal `-8`, see the package's ARCHITECTURE.md): the receiver sends `0x01 | receiver public key`; the sender answers `0x02 | sender public key`; the receiver checks it against the commitment.
3. HKDF over the ECDH secret (salt: sender key ‖ receiver key) gives the wrap key and a six-digit code. Both phones show the code (`SharePhase.verifyingCode`).
4. Only when the sender taps "Codes match" does it send `0x03 | nonce | K wrapped with the wrap key`. The receiver unwraps K, decrypts and opens the records.

The commitment makes the sender fix its key before seeing the receiver's, so a man in the middle cannot try keys until the two codes agree; with the sender's confirmation this protects the records' confidentiality. Receivers reject unencrypted (pre-encryption) payloads and older apps cannot open encrypted ones, so both phones need this version. Background receive mode (`ReceiveModeManager`) only holds the envelope; the share screen runs the exchange so the code is visible.

**Session lifecycle.**

- After "Codes match" the sender is in `SharePhase.awaitingViewer` until the receiver reports it is viewing. Every way out of that phase goes through `killSessionRequested`, since the receiver already has the key. If the kill can't be handed to the transport, the sender is told the other phone keeps the records until its timer ends (`remoteEndUnconfirmed`).
- The receiver ends the session when the connection drops, when the app is paused or hidden (not on `inactive`, which also covers Control Center and system prompts), when cancelled, or at expiry. Cancelling or leaving while decrypting stops the records from opening.
- Received notes are served from memory (`SharedNotesDatasource` behind `RecordsRepository.showSharedNotes`) and never written to `record_notes`, so they aren't synced and can't be left behind.
- Decrypted attachments live in `tmp/share_session_<id>/`, which is deleted by its own path when the session ends or the screen closes. `ShareRecordsService.sweepLeftovers()` runs at mobile startup and removes session folders and `share_*.bin` payloads left by a kill or crash.
- The share page owns screen protection from the moment records open until it closes, and pops anything opened on top of it (records, documents, dialogs) when the session ends.
- While a share screen owns the transport, receive mode is paused (`ReceiveModeService.isPaused`) and the app's lifecycle handler leaves it alone, so locking the phone doesn't cut a live share.

GitLab CI (`.gitlab-ci.yml`) on `git.lifevalue.com/mobile/health-wallet/app`.

- **checks**: every push, Linux runners, `debian:bookworm-slim` with Flutter cloned at the pinned tag (cirruslabs images stop at 3.44). Runs `flutter pub get`, `dart run build_runner build`, `flutter analyze --no-fatal-infos --no-fatal-warnings`, `flutter test`. No secrets.
- **ios:testflight / macos:testflight / android:play-internal**: automatic on `develop`, manual elsewhere (the branch must be protected to see protected variables). `shell-macmini` runner, fastlane `beta`, one `resource_group` each. Automatic signing: certificates in the runner's login keychain, profiles via the App Store Connect API key and `-allowProvisioningUpdates`. Android Gradle runs on Temurin JDK 17 (`ANDROID_JDK_*`, cached per runner, set through `org.gradle.java.home`).
- **shorebird:patch-android / shorebird:patch-ios**: manual on `master`.
- **windows:release**: manual on any branch; `master` → `v<version>`, others → `v<version>-dev.<pipeline iid>`; uploads zip + msix to the generic package registry and creates a GitLab Release. Needs a `windows` runner (none registered yet).
- Private pub dependencies are fetched with `CI_JOB_TOKEN` (the project must be on their job-token allowlists).
- Every `pod` call on the Mac mini runs the CocoaPods pinned in `ios/Gemfile` (1.17), through Bundler. cocoapods-core caps activesupport below 8, and every 7.x has GHSA-8474-xrp6-wh69, so the Gemfile raises that cap with the `bundler-override` plugin and requires activesupport ≥ 8.1.4.1; CocoaPods installs the pods unchanged on it. Bundler installs the plugin into the ignored `.bundle/` folder; nothing of it is committed. Remove the override once a CocoaPods release allows activesupport 8 (CocoaPods/Core#786).
